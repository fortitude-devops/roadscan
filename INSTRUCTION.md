# RoadScan — пошаговая инструкция на 5 часов

Кейс 9 HackAlem AI: выявление дефектов дорожного покрытия по фото и определение приоритета ремонта.
**Формат решения: веб-сервис.**

| Слой | Технология | Почему |
|---|---|---|
| Распознавание | локальный детектор RDD2022 + облачные VLM как резерв | работает офлайн, без квот; не привязано к вендору |
| Приоритет | детерминированный движок на Python | воспроизводим и объясним в баллах |
| Backend | FastAPI + Uvicorn | автоматический Swagger — API видно судьям |
| Frontend | статические HTML/CSS/JS, без сборки | нечему ломаться за 20 минут до защиты |
| Публикация | cloudflared-туннель с ноутбука | публичный https-адрес за 30 секунд |

Ключевое решение: **приоритет считает формула, а не языковая модель.** Модель отвечает только на вопрос «что видно на снимке» — тип дефекта и тяжесть 1–5. Место, трафик, погоду и близость школы добавляет прозрачный движок. Поэтому приоритет воспроизводим, раскладывается на факторы в баллах и настраивается без переобучения.

---

## Что уже работает в этом репозитории

Две страницы и полноценный REST API:

- `/` — **страница жителя**: мобильная, с доступом к камере телефона. Загрузил фото → получил тип дефекта, рамку, приоритет, срок реакции и разбор факторов.
- `/dashboard` — **дашборд управления дорог**: очередь ремонта по убыванию приоритета, KPI, карта Кызылорды, статусы заявок, выгрузка наряд-задания в CSV.
- `/docs` — **Swagger**: живая документация API. Показать её судьям — отдельные очки за «сервис», а не «скрипт».

Проверить всё без единого обращения к модели:

```bash
python selftest.py       # логика приоритета и качества снимков
python api_selftest.py   # весь HTTP-путь на заглушке модели
```

Обе проверки должны быть зелёными до того, как вы тронете код.

## Шаг 0. Подготовка (20 минут)

### 0.1 Модель распознавания

**Основной вариант — локальный детектор.** Скачайте веса под таксономию RDD2022 (CamThink Road Damage Detection или аналог) в формате `.onnx`, положите в папку `models/` и задайте в `.env`:

```
AI_PROVIDER=local
AI_PROVIDER_FALLBACKS=openrouter,gemini
```

Почему это лучший выбор для хакатона: работает без интернета, без квот и без «503 high demand», отвечает за 50–200 мс и обучен именно на дорожных дефектах, а не на всём подряд. Подробности и ссылки — в `models/README.md`.

Если весов пока нет, сервис молча перейдёт к облачному провайдеру из `AI_PROVIDER_FALLBACKS` — можно начинать работу сразу, а модель подключить позже.

### 0.1a Ключ облачного провайдера (резерв)

Сервис не привязан к одному вендору. В `.env` задаётся `AI_PROVIDER`, и это всё, что нужно поменять для перехода на другого поставщика.

**Рекомендуется OpenRouter.** Ключ бесплатно и без карты: https://openrouter.ai/keys

```
AI_PROVIDER=openrouter
OPENROUTER_API_KEY=sk-or-v1-...
```

Модель по умолчанию — `openrouter/free`: это роутер, который сам подбирает доступную бесплатную модель с поддержкой изображений. Упала одна — запрос уходит в другую, без вашего участия.

Поддерживаются также `gemini`, `groq`, `openai`, `mistral` и любой OpenAI-совместимый эндпоинт через `custom` (в том числе локальный Ollama).

> **Заведите ключи у двух разных провайдеров** и пропишите второй в `AI_PROVIDER_FALLBACKS`. Тогда перегрузка у одного вендора вообще не заметна: сервис перейдёт ко второму автоматически. На хакатоне это спасает демонстрацию.

### 0.2 Установка и запуск

**Самый быстрый путь:** `start.bat` на Windows (двойной щелчок) или `./start.sh` на macOS и Linux.
Скрипт создаёт окружение, ставит зависимости, прогоняет самопроверку, поднимает сервис
и открывает браузер. Повторные запуски занимают пару секунд.

Вручную, если нужен контроль над шагами:

```bash
cd roadscan
python -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env                 # Windows: copy .env.example .env
# впишите ключ в GEMINI_API_KEY

uvicorn api.main:app --host 0.0.0.0 --port 8000 --reload
```

Откройте три вкладки и держите их открытыми весь хакатон:

| Адрес | Что это |
|---|---|
| http://localhost:8000/ | страница жителя |
| http://localhost:8000/dashboard | очередь ремонта |
| http://localhost:8000/docs | Swagger |

`--host 0.0.0.0` обязателен: без него телефон в той же Wi-Fi сети не откроет сервис по IP ноутбука.

### 0.3 Тестовые фото — соберите заранее

Положите в `demo_images/` **20–25 фотографий**. Без них вы не отладите false positive, а это отдельный критерий оценки.

| Категория | Сколько | Зачем |
|---|---|---|
| Ямы разного размера | 5 | основной класс |
| Трещины (продольные, сетка) | 4 | второй тип по чек-листу демо |
| Колея / просадка | 3 | третий тип |
| **Нормальная ровная дорога** | **5** | критерий «false positive» |
| Ловушки: тени, лужи, люки, разметка, заплатки | 4 | здесь модель ошибается чаще всего |
| Плохие фото: тёмное, размытое, под углом | 3 | критерий «низкая уверенность» |

Снимите часть на телефон прямо у площадки — фото своего города в демо смотрятся сильнее стоковых. Называйте файлы осмысленно: `pothole_01.jpg`, `normal_01.jpg`, `trap_shadow_01.jpg`.

## Шаг 2. Час 0:30–1:30 — прогон на своих данных

Код рабочий, ваша задача — проверить его на реальных фото и поправить очевидное.

Откройте `/`, выберите участок «ZONE-03 Подъезд к школе №17», загрузите фото ямы. Должны увидеть класс дефекта, рамку, приоритет, срок реакции и разбор факторов. Затем откройте `/dashboard` — заявка уже там.

**A (ML).** Прогоните 10 фото, смотрите на поле `evidence` в ответе. Если модель пишет «тёмное пятно круглой формы» на фото с тенью — стоп-лист в `app/prompt.py` надо усилить именно этой формулировкой.

**B (логика).** Возьмите одно фото ямы и прогоните через `ZONE-03` (школа) и `ZONE-08` (двор). Разрыв должен быть очевидным. Если нет — двигайте `ROAD_TYPE_WEIGHT` и `PRIORITY_THRESHOLDS` в `app/config.py`. Ориентир калибровки: **высокий приоритет получают единицы заявок, а не большинство**, иначе очередь теряет смысл.

**C (backend).** Пройдите по `/docs` и прочитайте описания эндпоинтов глазами судьи. Правьте формулировки — Swagger вы будете показывать на защите.

**D (frontend).** Проверьте на реальном телефоне, а не в эмуляторе: кнопка камеры, размер шрифтов, скорость. Откройте с телефона `http://<IP-ноутбука>:8000`.

> **Контрольная точка 1:30 — сервис принимает фото и выдаёт приоритет.** Не дошли — бросайте остальное и доводите этот минимум.

## Шаг 3. Час 1:30–2:30 — неуверенность и объяснимость

Два критерия ТЗ, которые команды обычно забывают, а они дают отрыв.

**Неуверенность** реализована в `app/quality.py`: резкость по дисперсии Лапласиана, яркость, контраст, разрешение — всё считается до вызова модели. Итоговая уверенность = `уверенность модели × качество снимка`. Ниже 0.55 заявка помечается «требуется ручная проверка», а приоритет физически не может стать высоким.

Проверьте на своих плохих фото:

```bash
python analyze_cli.py "demo_images/bad_*.jpg" --road main_road
```

Должен появиться флаг `⚠️ручная`. Если нет — подкрутите `BLUR_THRESHOLD` в `config.py` под ваши снимки.

**Объяснимость** — блок «Почему такой приоритет» с полосками вклада каждого фактора. Убедитесь, что формулировки понятны неподготовленному человеку: не «коэффициент 1.5», а «Подъезд к школе (×1.5) → +3.45 балла».

**Заодно включите анонимизацию** (`app/privacy.py`, чекбокс на странице жителя) и проверьте на фото с машиной в кадре. Пункт «Безопасность» в ТЗ закрывается за 10 минут.

## Шаг 4. Час 2:30–3:15 — очередь ремонта

То, что превращает «классификатор картинок» в продукт для акимата.

Дашборд уже собирает заявки, сортирует по баллу, считает KPI, показывает карту, позволяет менять статус и выгружает наряд-задание. Ваша задача — **наполнить его до демо**: прогоните 10 фото по разным участкам. Судьи должны увидеть рабочий список, а не одну карточку.

Если остаётся время — впишите в `data/zones.csv` реальные улицы вашего города с настоящими координатами. Локальная привязка сильно поднимает восприятие.

## Шаг 5. Час 3:15–4:15 — борьба с false positive

**Не пропускайте этот час.** Отдельная строка в критериях, и здесь легче всего набрать очки, потому что большинство команд про неё забывает.

```bash
# главный тест: нормальная дорога не должна считаться дефектной
python analyze_cli.py "demo_images/normal_*.jpg" --expect none

# ловушки: тени, лужи, люки, разметка
python analyze_cli.py "demo_images/trap_*.jpg" --expect none

# обратная проверка: ямы не должны пропускаться
python analyze_cli.py "demo_images/pothole_*.jpg" --expect pothole
```

Внизу печатается точность. **Цель: не ниже 90% на `--expect none`.**

Цикл исправления:

1. Нашли ошибку → посмотрите, что модель написала в `evidence`
2. Откройте `app/prompt.py`, добавьте эту ситуацию в блок «ЭТО НЕ ДЕФЕКТЫ» максимально конкретно
3. Перезапустите с `--no-cache`, иначе получите старый закэшированный ответ
4. Повторяйте, пока точность не выйдет на плато

Формулировки, которые реально помогают: «тень от дерева с резкой границей», «влажное пятно после дождя на ровном покрытии», «крышка люка вровень с покрытием», «стёртая разметка».

> Осторожно с перегибом: перекачаете стоп-лист — начнёте пропускать настоящие ямы. Каждые 15 минут прогоняйте обратный тест.

## Шаг 6. Час 4:15–4:40 — публикация в интернет

Сервис крутится на ноутбуке, а судьям нужен адрес, который открывается с их телефона. Туннель делает это за 30 секунд и не требует деплоя.

```bash
# macOS
brew install cloudflared
# Windows: winget install --id Cloudflare.cloudflared
# Linux: скачайте бинарник с github.com/cloudflare/cloudflared/releases

cloudflared tunnel --url http://localhost:8000
```

В консоли появится адрес вида `https://random-words-1234.trycloudflare.com` — публичный, с https, работает с любого телефона. Регистрация не нужна.

Альтернатива, если cloudflared не ставится: `ngrok http 8000` (нужен бесплатный аккаунт) или `ssh -R 80:localhost:8000 serveo.net` (ничего ставить не надо).

### Козырь демо: QR-код

```bash
pip install "qrcode[pil]"
python -c "import qrcode,sys; qrcode.make(sys.argv[1]).save('qr.png')" https://ваш-адрес.trycloudflare.com
```

Выведите QR на слайд. Судьи сканируют, выходят на парковку у площадки, фотографируют реальную выбоину — и она появляется в вашем дашборде **при них, в реальном времени**. Это закрывает пункт чек-листа «проверить систему на новом изображении от судей» самым убедительным способом.

### Если нужен настоящий деплой

В репозитории есть `Dockerfile`, готовый для Render, Railway и Fly.io: они подставляют свой `$PORT`, контейнер это учитывает. Не забудьте задать `GEMINI_API_KEY` в переменных окружения сервиса. Закладывайте 20–30 минут и делайте это **только после** того, как туннель уже работает — деплой не должен быть единственным путём к демо.

## Шаг 7. Час 4:40–5:00 — репетиция

### Чек-лист из ТЗ — прогоните буквально

| № | Пункт ТЗ | Что показываете | Готово |
|---|---|---|---|
| 1 | Нормальная дорога | `normal_01.jpg` → «Дефект не выявлен» | ☐ |
| 2 | Определить яму | `pothole_01.jpg` → класс, рамка, описание | ☐ |
| 3 | Второй тип дефекта | `crack_01.jpg` → трещина | ☐ |
| 4 | Тот же дефект в разном контексте | `ZONE-03` школа → **Высокий**, затем блок «Тот же дефект в другом месте» → двор → **Низкий** | ☐ |
| 5 | Новое фото от судей | QR-код → их телефон → их снимок | ☐ |

Сверх чек-листа, на что обращают внимание: плохое фото → «требуется ручная проверка»; разбор приоритета по факторам; очередь ремонта с картой и выгрузкой CSV; Swagger как доказательство, что это сервис, а не скрипт.

### Сценарий на 4 минуты

- **0:00–0:30 — проблема.** «Заявки приходят из пяти каналов, приоритет расставляется вручную и субъективно. Яма у школы может ждать дольше, чем яма во дворе.»
- **0:30–1:30 — базовая работа.** Нормальная дорога → нет дефекта. Яма → есть, с рамкой. Трещина → второй класс.
- **1:30–2:30 — главный козырь.** Одно фото, два контекста, разный приоритет. Показываете разбор по факторам: «приоритет считает не нейросеть, а прозрачная формула, её можно утвердить регламентом».
- **2:30–3:00 — честность системы.** Тёмное фото → низкая уверенность → ручная проверка. «Система не притворяется, что знает.»
- **3:00–3:30 — продукт.** Дашборд, карта, наряд-задание, Swagger.
- **3:30–4:00 — QR и фото судей** живьём.

### Страховка на случай отказа интернета

Ответы модели кэшируются в `cache/` по хэшу изображения. Перед демо прогоните весь `demo_images/` один раз:

```bash
python analyze_cli.py "demo_images/*.jpg"      # наполняет кэш
echo "OFFLINE_MODE=1" >> .env                  # если Wi-Fi упал
```

В офлайне живое фото судей не отработает, поэтому держите телефон с раздачей интернета как второй запасной вариант. И помните: туннель тоже требует сети — при её потере показывайте с `localhost`, проецируя экран.

## Карта API

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/analyze` | анализ снимка: дефект, приоритет, факторы |
| POST | `/api/what-if` | пересчёт приоритета в другом контексте без вызова модели |
| GET | `/api/reports` | очередь ремонта, фильтры по приоритету и статусу |
| GET | `/api/reports/{id}` | полная карточка заявки |
| GET | `/api/reports/{id}/image` | снимок с отрисованной рамкой |
| PATCH | `/api/reports/{id}/status` | смена статуса: новая → в работе → выполнено |
| GET | `/api/reports/stats` | сводка для KPI |
| GET | `/api/export.csv` | наряд-задание для Excel |
| GET | `/api/zones`, `/api/dictionaries` | справочники для фронтенда |
| DELETE | `/api/reports` | очистить очередь перед демо |

Пример интеграции для внешней системы — ровно то, что стоит показать, если спросят про масштабирование:

```bash
curl -X POST https://ваш-адрес/api/analyze \
  -F "file=@road.jpg" \
  -F "zone_id=ZONE-03" \
  -F "weather=wet"
```

## Что говорить про архитектуру

> «Мы разделили восприятие и решение. Мультимодальная модель отвечает только на вопрос "что видно на снимке" — тип дефекта и тяжесть. Приоритет ремонта считает детерминированный движок на контексте участка: тип дороги, трафик, погода, близость школы или перехода. Поэтому приоритет воспроизводим, объясним в баллах и может быть утверждён как регламент, а не остаётся решением чёрного ящика. Чтобы изменить политику приоритизации, акимату не нужно переобучать модель — достаточно поменять веса в конфиге. Бизнес-логика вынесена в отдельный слой и не зависит от фреймворка, поэтому сервис одинаково работает как веб-приложение, как REST API для интеграции с eGov и как бэкенд мобильного приложения.»

## Типичные проблемы

| Симптом | Причина и решение |
|---|---|
| `Не задан GEMINI_API_KEY` | Файл называется ровно `.env` и лежит в корне проекта. У Windows часто выходит `.env.txt` |
| `404 model not found` | `vision.py` сам подберёт доступную flash-модель. Не помогло — задайте `GEMINI_MODEL` в `.env` |
| `429 Resource exhausted` | Лимит бесплатного тарифа. Переключитесь на второй ключ, кэш сохранится |
| `503 This model is currently experiencing high demand` | Бесплатный тариф перегружен. Сервис сам делает 3 повтора с паузой и переключается на запасную flash-модель. Если не помогло — подождите минуту. **Перед демо обязательно прогрейте кэш**, иначе рискуете попасть на перегрузку при судьях |
| Телефон не открывает сервис | Запускайте с `--host 0.0.0.0` и открывайте по IP ноутбука, не по `localhost` |
| Карта на дашборде не появляется | Leaflet грузится с CDN; без интернета блок скрывается сам. Таблица и KPI работают всегда |
| Ответ идёт 10+ секунд | Уменьшите `MAX_IMAGE_SIDE` в `config.py` до 768 |
| Модель видит ямы везде | Усильте блок «ЭТО НЕ ДЕФЕКТЫ» в `prompt.py`, прогоните `--expect none --no-cache` |
| Правки промпта не применяются | Включён кэш. Запускайте с `--no-cache` |
| Кириллица на картинке кракозябрами | Так и задумано: OpenCV не умеет кириллицу, подпись на рамке латиницей. Весь остальной текст — в интерфейсе |
| Очередь не обнулилась перед демо | `curl -X DELETE http://localhost:8000/api/reports` |
